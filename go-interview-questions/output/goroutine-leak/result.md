# goroutine-leak 运行结果

**对应题目**：七、goroutine 泄漏
**目的**：确认两种泄漏形态对协程数的影响、修复版本是否真的归零，以及线上如何观测
**运行方式**：`cd code/goroutine-leak && go run .`
**原始输出**：`result.txt`（stdout）

## 关键输出

```
起始协程数：1

leakBySend() 调用 100 次        协程数   1 -> 101（变化 +100）
leakByContext() 调用 50 次      协程数 101 -> 151（变化 +50）

修复版本：
fixedByBuffer() 调用 100 次     协程数 151 -> 151（变化 +0）
fixedByCancel() 调用 100 次     协程数 151 -> 151（变化 +0）

main.leakByContext.func1()       出现 50 次
main.leakBySend.func1()          出现 100 次
当前仍在运行的协程数：151
```

## 结论

整个过程**没有任何错误输出**——没有 panic，没有日志，没有告警。协程数从 1 涨到 151，程序跑得好好的。这就是它危险的地方：它不在错误预算里，在内存预算里。

修复版本的效果干净：channel 缓冲够用时发送方不必等人接就能退出；显式调用 `cancel()` 后等取消的协程被唤醒。两种修复的协程数变化都是 0。

线上观测方式：把所有协程的转储打出来，同一处调用帧会重复出现成百上千次，这就是 goroutine profile 里的样子。
